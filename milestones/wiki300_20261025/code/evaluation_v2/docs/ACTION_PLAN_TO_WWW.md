- Gold要同时核正常前缀正文、违规原文及来源修订ID、更早公开历史、过滤/移动日志和区间开闭边界。两名真人独立做证据审阅，第三方或记录仲裁解决分歧；AI只提出证据和建议，不冒充两个人。
- 新旧账号的全部训练/验证/测试必须按账号及已知关联关系分组，避免同一人、同一已知关联团伙跨组。Gold前缀弱/强、检测延迟短/长、区间宽/窄分别报告。若Gold不足则缩小科研主张，不伪造更多。

## 模型下一版必须改的3个定义和2个模块

定义：①`tf_obs`是公开记录中可核查违规起点/区间，不是恶意“意图”首次出现；②`td`在Wiki中是相关首次封禁（处置代理），不是第一次发现；③`normal`是右删失观察窗而非终生正常。

模块：①评分器按EXACT事件、EXACT UTC、INTERVAL、CENSORED分流（本包已有纯评分补丁，后续与仓库CI整合）；②特征管线从8维累计元数据升级为**同时记录编辑级局部变化与跨编辑历史**，但要先核查所有正常/违规来源的正文覆盖率，单独版本、保持旧结果复现。

优先实验：在同一账号上比较现有冻结融合、Behavior-only、Delay-only、随机/中点/末端朴素基线；只用训练/验证确定先验和参数。若新语义/局部特征在VAL没有改善，不应无原则地加入。原TEST已经看过，后续调参不可再把它当最终盲测。

## API、算力和沟通分工

- 不需要先买服务器/GPU：这轮300个账号的双高斯EM模型和指标CPU就能运行，现有首轮已经完成。
- 需要提高采集速度时优先使用**已有3540条贡献历史缓存**和修订ID查询，而不是再随机扫4,000个账号。
- 公开证据通过 Wikipedia MediaWiki `usercontribs` / `compare` / `logevents` / `abuselog` 拉取，仅补缺失的修订正文；保存API原文、URL、缓存键、请求时间和失败记录；遵守描述性User-Agent、maxlag、429 Retry-After 和限速。
- LLM API是**可选的批量证据判读器**，不是训练该EM模型的必需品。配置含额度的API后先做20案试运行，记录每个案子的token、金额、错误和可核验接纳率；只有相对人工审阅准确才放大25案批次。AI的stdout应为结构化JSON：账户ID、标签类型、起点证据、正常前缀证据、排除更早行为依据、风险标志、缺失说明。
- 若用户希望全天连续采证，必须在其**本人电脑或服务器**运行既有有断点的worker。聊天断线不会自动接管其服务器；使用本地SQLite、checkpoint、锁和回退。OpenAI API密钥使用环境变量，绝不可提交GitHub。

## 如何解释“4000候选只有300收录”

4166身份池和3540已缓存历史 ≠ 已逐条人工语义核验的4166账号；最终200转变和额外100对照来源于两个不同的采样路线。最近一次针对转变的深审41个新增25个，接纳率约61%；正常对照人工内容审查271个接纳100个，约37%。所以真正的问题是初筛、候选目的、证据补齐、前缀质量匹配，而不是简化成“看了4000个只有300个可用”。后续用“每100个深审可拿多少合格样本”和“每个合格样本人工时间/模型费用”衡量效率，不用“缓存用户数”评估标注产能。
